# 架构与目录约定

本文档说明 `nomitr-blog` 单仓库的划分依据与边界规则。目录树本身见根 `README.md`，这里解释"为什么这么分"和"新东西该放哪"。

## 1. 目标

1. **一个仓库装完一个博客**：前台、后台、接口、内容、部署配置同仓，克隆一次即可开发。
2. **边界清晰**：每个目录的职责写下来，减少"这个文件到底该放哪"的争论。
3. **应用可独立演进**：`apps/*` 各自选择技术栈、各自部署，互不牵制。
4. **内容与代码解耦**：文章是数据，不是源码；写作流程不依赖开发者。

## 2. 分层模型

```text
┌──────────────────────────────────────────────┐
│ apps/          可运行、可部署的应用           │
│  web（前台）  admin（后台）  api（服务端）     │
└───────────────┬──────────────────────────────┘
                │ 只能向下依赖
┌───────────────▼──────────────────────────────┐
│ packages/      不部署的共享库                 │
│  ui（组件）  shared（类型/工具）  config（配置）│
└───────────────┬──────────────────────────────┘
                │ 读取
┌───────────────▼──────────────────────────────┐
│ content/       文章与素材（数据，不是代码）    │
└──────────────────────────────────────────────┘

横切关注点：docs/（文档）、scripts/（工程脚本）、deploy/（部署编排）
```

### 依赖方向

```text
apps/web ─┐
apps/admin ├──▶ packages/ui ──▶ packages/shared
apps/api ─┘         │                 │
                    └──────┬──────────┘
                           ▼
                    packages/config（工程配置，构建期引用）
```

## 3. 边界规则

| 规则 | 说明 | 违反后果 |
| --- | --- | --- |
| 应用之间禁止互相 import | 共享代码下沉到 `packages/` | 形成隐式耦合，无法单独部署 |
| `packages/*` 禁止引用 `apps/*` | 共享库必须脱离应用可编译 | 循环依赖、构建顺序失控 |
| 只从包入口 import | 禁止 `@nomitr/ui/src/...` 深路径 | 内部重构变成破坏性变更 |
| `content/` 不放代码 | 文章目录只存 Markdown 与素材 | 内容与逻辑混杂，写作流程被拖住 |
| `docs/`、`scripts/`、`deploy/` 不放业务逻辑 | 这三个目录是支撑设施 | 运行时逻辑散落，测试与部署困难 |
| 根 `package.json` 不放业务依赖 | 只在根放脚本与公共元信息 | 隐式全局依赖，工作区隔离失效 |

判断一段代码归属的三个问题：

1. 它需要被别的应用复用吗？→ 是：`packages/`。
2. 它只有某个应用能用吗？→ 是：该应用的 `src/`。
3. 它是数据或配置吗？→ 是：`content/` 或 `deploy/`。

## 4. 新增东西该放哪

| 要加的东西 | 放哪 | 备注 |
| --- | --- | --- |
| 新页面 | `apps/web/src/pages/` 或 `apps/admin/src/pages/` | 按面向对象区分 |
| 两边都要用的按钮 | `packages/ui/src/components/` | 从包入口导出 |
| 新的数据类型 | `packages/shared/src/types/` | 前后端共用一份 |
| 接口 | `apps/api/src/modules/<域>/` | 一个业务域一个模块 |
| 一篇新文章 | `content/posts/YYYY-MM-DD-slug.md` | 用脚本生成模板 |
| 构建脚本 | `scripts/` | 命名 `kebab-case`，带 `--help` |
| 新的部署目标 | `deploy/<平台>/` | 一应用一目录 |
| 一次架构决策 | `docs/adr/NNNN-标题.md` | 按序号递增 |
| 新的可部署应用 | `apps/<name>/` | 同步更新 `apps/README.md`、根 README、本文依赖图 |

## 5. 工作区与发布

- 工作区成员由 `pnpm-workspace.yaml` 声明，只有 `apps/*` 与 `packages/*` 会被安装依赖。
- `packages/*` 默认 `private: true`，只在本仓使用；若将来要发布，必须先在 README 说明版本策略。
- `apps/*` 各自独立构建、独立部署，构建顺序由依赖图决定（`config` → `shared` → `ui` → 应用）。
- 根脚本用 `pnpm -r --if-present <task>` 转发，模块实现该任务后自动接入流水线。

## 6. 从扁平结构迁移

如果代码原本堆在同一层（例如 `src/` 里混着页面、组件、接口），按下面的映射搬：

| 原位置 | 新位置 |
| --- | --- |
| 站点页面、路由 | `apps/web/src/pages/` |
| 后台页面 | `apps/admin/src/pages/` |
| 服务端接口与数据访问 | `apps/api/src/modules/` |
| 通用组件 | `packages/ui/src/components/` |
| 工具函数、类型、常量 | `packages/shared/src/{utils,types,constants}/` |
| 根级 lint / 构建配置 | `packages/config/` |
| 散落的 `.md` 文章 | `content/posts/` |
| 图片素材 | `content/assets/` |
| 架构说明、流程图 | `docs/` |
| 一次性脚本 | `scripts/` |

迁移顺序建议：先建目录骨架并提交一版（当前已完成的动作），再按"内容 → 共享库 → 应用"分批搬，每批搬完跑一次构建，避免大爆炸式重构。

## 7. 维护约定

- 目录调整必须与文档同提交，`docs/architecture.md` 与根 README 的目录树保持一致。
- 每次新增 `packages/*` 成员，都要在 `packages/README.md` 的表格里补一行。
- 超过一年没被引用的共享包，评估删除，避免仓库膨胀。
