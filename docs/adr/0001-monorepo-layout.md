# 0001. 采用单仓库分层目录结构

- 状态：已接受
- 日期：2026-10-25

## 背景

博客项目需要同时容纳面向读者的前台站点、面向作者的管理后台、提供数据的后端服务，以及文章内容本身。这几部分共享同一套数据模型与视觉规范，但在开发节奏和部署方式上又互相独立。

此前仓库没有固定的分层：代码、文章、配置混在同一层，导致三个问题：

1. 新文件不知道该放哪，同名目录（`components`、`utils`）在不同位置重复出现。
2. 前台与后台各自复制了一份组件和类型，改一处要改两处。
3. 文章与代码混放，写作流程和发布流程互相干扰。

## 备选方案

1. **多仓库（multi-repo）**：前台、后台、接口、内容各一个仓库。
   - 优点：每个仓库边界天然清晰，权限与发布独立。
   - 缺点：共享代码只能靠发包或复制；一次跨端改动要开多个 PR，版本对齐成本高；个人博客体量下属于过度拆分。

2. **单仓库扁平结构**：一个仓库，所有代码平铺。
   - 优点：起步最快。
   - 缺点：就是当前的状态——边界靠自觉，时间一长必然混乱，无法单独构建某个应用。

3. **单仓库分层结构（monorepo + workspace）**：
   - 优点：边界由目录强制表达；共享代码是本地包，改完立即生效；应用可独立构建部署；内容与代码分离。
   - 缺点：需要维护工作区配置与依赖方向约定。

## 结论

采用方案 3：单仓库，按 `apps/`（可部署应用）、`packages/`（共享库）、`content/`（内容数据）、`docs|scripts|deploy`（支撑设施）分层，用 pnpm workspace 声明成员，依赖方向只允许 `apps → packages`。

## 影响

- 新增 `pnpm-workspace.yaml` 与根 `package.json`，根脚本统一用 `pnpm -r --if-present` 转发。
- 新增 `apps/{web,admin,api}` 与 `packages/{ui,shared,config}` 六个工作区成员，各自持有 `package.json`（`private: true`）。
- 文章统一迁入 `content/posts/`，命名 `YYYY-MM-DD-slug.md`，草稿目录不入库。
- 目录与依赖规则写入 `docs/architecture.md`，结构变更需与文档同提交。
- 后续若引入真正的多团队协作，可保持本结构不变，仅把 `apps/*` 拆出为独立仓库；`packages/*` 的边界已经按"可独立发布"预留。
